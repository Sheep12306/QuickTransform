# QuickTransform 项目架构文档

> Word（.docx）转 Markdown（.md）工具
> 文档版本：v0.2　最后更新：2026-09-21
> 状态：核心决策已确认（个人使用 / 本地网页版 / 完全离线 / Python），可转入开发

---

## 1. 项目背景

### 1.1 痛点

进销存产品的需求文档、字段清单、权限矩阵、状态机说明，当前主要沉淀在 Word 里。但 Word 格式天然不适合做下面这些事：

| 想做的事 | Word 的障碍 |
| --- | --- |
| 喂给 AI 做需求分析、生成 PRD、做完备性审查 | Word 是二进制容器，内容不能被文本工具直接读取 |
| 放进 Git / 知识库做版本管理和 diff | 二进制文件无法逐行对比，看不出改了哪一句 |
| 复制到飞书、Notion、语雀等协作平台 | 手工粘贴会丢失标题层级、表格结构、列表编号 |
| 复用文档里的字段表 | 表格跨文档搬运只能一格一格复制 |

手工“另存为纯文本”或逐段复制粘贴的代价是：标题层级全丢、表格塌成一行、编号列表变成乱码，返工时间往往超过文档本身的价值。

### 1.2 项目目标

做一个本地运行、离线可用、一次点击完成转换的工具，把 Word 文档高保真地转成结构清晰、可直接使用的 Markdown。

具体目标：

1. **保真优先**：标题层级、列表编号、表格结构、图片、超链接、加粗斜体等语义必须正确还原。
2. **可解释**：每次转换都产出转换报告，明确告诉你哪些内容被降级处理了、降级成了什么，而不是悄悄丢掉。
3. **零心智负担**：不需要懂命令行、不需要装环境、不需要联网，拖进文件就能拿到结果。
4. **可批量**：支持一次转换整个目录，用于历史文档库迁移。
5. **隐私安全**：文档不出本机。进销存文档常含客户名、价格、供应商信息，绝不上传到外部服务。

### 1.3 非目标（本期明确不做）

| 不做的事 | 原因 |
| --- | --- |
| 扫描件 / 图片型 PDF 的 OCR | 属于另一套技术栈（OCR 模型），先不混进来 |
| Markdown 反向转 Word | 有价值，但属于独立能力，放到后期评估 |
| 在线协作、云端存储、多人权限 | 与本地优先、隐私优先的定位冲突 |
| 富文本在线编辑器 | 不是本项目要解决的问题 |

## 2. 使用场景

### 场景 A：单篇转换（高频，主场景）

写好的 PRD.docx 转成 PRD.md，粘进 AI 对话继续做需求分析，或提交到 Git。

关键要求：快（秒级）、一步到位、结果可核对。

### 场景 B：批量迁移（一次性，但量大）

历史积累的几十上百篇文档一次性转成 Markdown，建知识库。

关键要求：能批处理、单个文件失败不影响整体、最后有一份汇总报告能看到哪些文件需要人工介入。

### 场景 C：作为上游被调用（后期）

被其他流程当作一个转换步骤调用，例如自动化的文档处理流水线。

关键要求：稳定的接口契约（命令行或 HTTP API）。

## 3. 需求范围

### 3.1 功能需求（按优先级）

**P0 必须实现**

- 段落与标题层级识别（多级标题映射到 `#` 至 `######`）
- 加粗 / 斜体 / 删除线 / 行内代码
- 有序列表与无序列表（含嵌套层级）
- 基础表格（转换为 GFM 表格）
- 图片提取到本地资源目录，并在正文对应位置插入引用
- 超链接（保留链接文字与地址）
- 输出转换报告（警告 + 统计信息）

**P1 重要**

- 合并单元格表格的降级处理（填充或转 HTML 表格）
- 表格单元格内的多段落、换行、列表
- 文档元信息（标题、作者、创建时间）输出为 YAML front matter
- 批处理：整个目录递归转换
- 网页上传界面（拖拽 / 多选）

**P2 增强**

- 脚注、尾注、题注
- 批注提取为独立清单
- 修订痕迹处理（接受 / 保留标记 / 输出对比）
- 公式 OMML 转 LaTeX
- 自动生成目录
- 自定义样式映射表（把中文样式名映射到语义角色）

### 3.2 非功能需求

| 维度 | 要求 |
| --- | --- |
| 保真度 | 结构元素（标题 / 列表 / 表格 / 图片）还原率不低于 98%；无法还原的必须进报告 |
| 性能 | 单篇 10MB 以内的文档，转换耗时不超过 3 秒 |
| 隐私 | 全程本地处理，无任何网络请求 |
| 可用性 | 无技术背景用户无需阅读文档即可完成单篇转换 |
| 可移植 | 在未安装任何运行环境的 Windows 机器上可直接使用 |
| 幂等性 | 同一输入文件重复转换，输出字节级一致 |
| 联网 | 不联网、不调用任何外部 API、不依赖大模型（见 3.3） |

### 3.3 运行方式：完全离线，且不接入大模型

这一条是硬约束，不是可选项。

**转换本身不需要联网。** 整个过程是本地计算：解压一个 ZIP 包、解析其中的 XML、写出文本文件。没有任何环节需要网络。

**大模型在转换环节不仅不需要，而且有害：**

- **转换要求确定性**。同一份文档转两次，结果必须完全一致；而大模型的输出是概率性的，做不到可复现。
- **大模型有改写倾向**。它可能顺手把采购订单数量润色成采购数量，或者自己补一个它认为合理的表头。对需求文档而言这是灾难，因为字段名、状态值、编号规则一旦被改动，你很难发现。
- **文档含客户名、价格、供应商信息**，上传到任何第三方服务本身就是风险。

**大模型真正有价值的位置在下游，不在转换环节。** 转换完成后，把 Markdown 喂给 AI 做需求完备性审查、生成测试用例、检查字段约束冲突，这些是理解内容的任务，适合大模型。

**职责边界**：本工具到产出一份干净的 Markdown 为止。职责单一，工具才可靠、才可复现。

## 4. 关键难点与设计取舍

这一节是本项目的含金量所在。Word 转 Markdown 听起来是个小功能，但真正决定成败的是下面这些细节。

### 4.1 难点一：标题识别不能只看样式名

**问题**：最直觉的做法是读段落的 `pStyle`，看到 `Heading 1` 就输出 `#`。但实际文档里会翻车：

- 中文版 Word 的样式名可能是 `标题 1`，也可能是用户自定义的 `一级标题`、`章节标题`
- 很多文档根本不用样式，而是手打 `1.1 需求背景` 然后把字号调大加粗
- 样式名相同但实际大纲级别不同（复制粘贴后样式串了）

**方案**：采用三级判定策略，按可靠性从高到低：

1. **样式定义优先**：解析 `styles.xml`，读样式自身及其 `basedOn` 父链，取 `outlineLvl` 属性。这是 Word 里大纲级别的权威来源，比样式名可靠。
2. **样式名启发式**：对 `Heading N`、`标题 N`、`一级标题`、`N 级标题` 等常见命名做匹配，作为补充。
3. **直接格式兜底**：对没有样式的段落，用字号显著大于正文、加粗、短文本、不含句号这组特征推断标题；置信度低的只记入报告，不强行转换。

**关键约束**：宁可少转一个标题，也不要乱转。误判会把普通段落变成标题，破坏整个文档结构，比漏转更难发现。

### 4.2 难点二：编号列表需要还原 Word 的计算结果

**问题**：Word 的列表编号不在段落文本里，而是靠 `numbering.xml` 里的定义动态算出来的。段落只带一个 `numId` 和 `ilvl`，实际显示的编号由列表定义、当前层级、前面的兄弟项共同决定。更麻烦的是：

- 无序列表的符号可能是 `•`、`-`、`▪`，有序列表可能是 `1.`、`a)`、`一、`、`①`
- 列表可以从 5 开始（`start=5`），甚至续接上一段被正文打断的列表
- 存在 `lvlOverride` 覆盖起始值的情况

**方案**：写一个列表状态机，遍历时维护每个 `numId` 的当前计数栈。解析到列表段落时先算出它实际显示的编号值，再映射到 Markdown：

- 无序列表输出 `-`
- 有序列表统一输出 `1.`（Markdown 渲染器会自动编号，且这样 diff 更稳定）
- 起始值非 1、或需要续接编号这类 Markdown 表达不了的情况，输出显式数字并记入报告
- 嵌套层级每层缩进 4 空格，避免与中文全角字符混排时的渲染歧义

### 4.3 难点三：表格合并单元格（最容易毁掉文档质量的地方）

**问题**：进销存文档的字段清单表、权限矩阵大量使用合并单元格。而 GFM 表格在语法上完全不支持合并单元格，这是硬限制，没有完美解。横向合并由 `gridSpan` 表达，纵向合并由 `vMerge` 的 `restart` / `continue` 表达。

**表格转换的难度并不均匀。** 按难度分四档：

| 档位 | 表格特征 | 转换结果 | 建议 |
| --- | --- | --- | --- |
| 容易 | 规整的行列，有表头，无合并 | 可完全可靠转换 | 无需额外处理 |
| 中等 | 单元格内有多段落、换行、列表，或含竖线字符 | 需要压平，用换行标签或项目符号连接，可自动完成 | 无需额外处理 |
| 困难 | 存在合并单元格（横向合并、纵向合并） | Markdown 语法层面不支持，只能降级，无法保真 | 见下方三种策略 |
| 极难 | 嵌套表格；用空格或制表位排版、在 OOXML 层面根本不是表格的伪表格 | 嵌套表格必须转 HTML；伪表格依赖启发式识别，存在误判风险 | 尽量从源头避免 |

补充几个容易被忽略的情况：

- **表头跨页重复**：只在 Word 打印时有意义，转 Markdown 后忽略即可
- **超宽表格**（20 列以上）：能转，但渲染时需横向滚动，可读性差，可考虑改用列表表达
- **单元格内放图片**：语法上可行，但多数 Markdown 渲染器在表格单元格内显示图片的效果很差

**方案**：提供三种策略，默认自动选择：

| 模式 | 行为 | 适用场景 |
| --- | --- | --- |
| `gfm` | 合并单元格的值重复填充到每个格子；纵向合并用上一行的值补全 | 表格结构规整，后续要进知识库检索 |
| `html` | 输出内联 HTML `<table>`，用 `colspan` / `rowspan` 真实还原 | 合并复杂、需要视觉保真 |
| `flatten` | 每行降级为表头加值的形式 | 表格只是为了排版，本质是键值对 |

**自动选择规则**：无合并走 `gfm`；存在合并时默认 `gfm`（重复填充，检索友好）；若合并层数超过 2 层，或存在纵向合并且列数超过 8，判定为复杂表格，改用 `html` 并写入报告提示。

**单元格内部内容的处理**（同样高频）：

- 单元格内多个段落，用 `<br>` 连接
- 单元格内换行，用 `<br>`
- 单元格内的竖线字符，转义为 `\|`（否则表格结构会被破坏）
- 单元格内的列表，拼接为有序的项目片段

### 4.4 难点四：图片与浮动定位

**问题**：图片以二进制形式存在 `word/media/` 里，正文通过关系 ID（`r:embed`）引用。图片可能是行内，也可能是浮动（带文字环绕）。Markdown 只有行内图片语法，表达不了浮动定位和尺寸。

**方案**：

- 提取图片到 `assets/文档名/` 目录，文件名规则化为 `文档名-img-001.png`，保证可读、可排序、不重名
- 按文档顺序在正文对应段落位置插入图片引用
- `alt` 文本优先取图片的替代文字（`docPr` 的 `descr`），为空则用占位文本并记入报告
- 浮动图片统一降级为行内，插入到其锚点所在段落之后，并记入报告
- 尺寸信息 Markdown 表达不了，需要时用 HTML 的 img 标签指定宽度；默认丢弃，因为大多不是内容语义
- 高清截图常达到数 MB，报告里统计图片总体积，提示是否需要压缩

**澄清一个常见误解：图片转换其实比表格简单得多。**

图片提取在技术上几乎是机械操作：图片以文件形式存放在 `word/media/` 目录中，正文通过一个关系 ID 引用它。程序只需要读 ID、找到文件、复制到本地资源目录、在正文原位置写入图片引用。**位置信息是完整的，不需要人工介入。**

所以不建议默认使用占位符方案，理由是它反而增加工作量：原本可以自动完成的事，变成每张图都要手动插一遍，而且你还得回头去找图片文件在哪里。

真正需要动脑的只有两件事：

1. **浮动图片（文字环绕）**：图片不在正文流里，而是挂在某个段落上并指定了位置。Markdown 只有行内图片语法，只能把它降级到锚点段落附近，位置与 Word 中会有差异。这一项必须记入报告。
2. **图片里的信息变成死内容**：这是真正的损失。如果流程图、状态机图是截图，转成 Markdown 后图片内部文字不可检索，喂给 AI 时也读不到。表格转成 Markdown 是活的结构，截图是死的像素。

**占位符模式的正确用途**：不是用来代替图片提取，而是作为可选模式，服务于你只想先拿到纯文字骨架的场景，图片位置用注释标出，后续自己决定插哪张。默认自动提取，占位符作为一条配置项保留。

### 4.5 难点五：无法无损表达的内容如何降级

Markdown 表达力有限，这些内容必须明确降级策略，且必须写进报告：

| Word 内容 | 降级方案 |
| --- | --- |
| 字体、字号、颜色、行距 | 丢弃（Markdown 无对应语义），但加粗 / 斜体 / 删除线保留 |
| 页面设置、页眉页脚、水印 | 丢弃 |
| 分页符 | 可配置：删除 / 转为分隔线 |
| 软换行 | 行尾加两个空格，实现 Markdown 硬换行 |
| 文本框、艺术字 | 抽取其中文本追加到所属段落，记入报告 |
| 公式（OMML） | 转 LaTeX 行内公式；转不了的降级为图片 |
| 旧版 OLE 公式对象 | 无法解析，转图片并记入报告 |
| 批注 | 可配置：丢弃 / 提取为文末批注清单 |
| 修订痕迹 | 默认接受全部修订（保留插入、丢弃删除） |
| 嵌入的 Excel 对象 | 忽略并记入报告 |

### 4.6 难点六：中文排版细节

- **全角空格（U+3000）必须原样保留**，它是中文文档缩进的常见写法，删掉会破坏内容
- **中英文之间的空格不做自动美化**：自动加空格会改动原文，导致 diff 噪音，也让 PM 无法确认转换是否忠实
- **不转换全角 / 半角引号**，保持原样
- **标题里已经含有人工编号**（如 `3.2 采购订单`）时不再额外加编号，直接保留文本

### 4.7 字体与字符格式能否正确转换

答案分三类，取决于 Markdown 有没有对应的表达方式。

**第一类：能准确转换**

| Word 格式 | Markdown 表达 | 说明 |
| --- | --- | --- |
| 加粗 | 双星号包裹 | 需处理样式与直接格式的叠加，见下文 |
| 斜体 | 单星号包裹 | 直接映射 |
| 删除线 | 双波浪号包裹 | 直接映射 |
| 行内等宽字符 | 反引号包裹 | 直接映射 |
| 超链接 | 链接语法 | 保留链接文字与地址 |
| 上标 / 下标 | 无原生语法 | 用 HTML 的上标下标标签 |

**第二类：Markdown 没有对应表达，只能丢弃**

字体（宋体 / 黑体 / 微软雅黑）、字号、字体颜色、字符底纹、行距、缩进、段落对齐、页面设置。

这些属于排版而非语义，而 Markdown 的设计哲学就是只保留结构、不含排版信息。丢弃不影响内容，但要有心理预期：转出来的 Markdown 在视觉上不会长得像原来的 Word，这是格式本身的特性，不是工具能力不足。

**第三类：有争议，需要做决策**

| 格式 | 可选处理 | 建议 |
| --- | --- | --- |
| 文字突出显示（高亮） | 转 HTML 高亮标签 / 丢弃 | 默认丢弃，记入报告 |
| 下划线 | 转 HTML 下划线标签 / 改用加粗 | 默认丢弃，Markdown 里连续的星号或下划线是强调语法，不可混用 |
| 整段加粗 | 保留加粗 / 作为标题候选 | 中文文档里整段加粗常被当作小标题使用，可作为标题推断的线索 |

**一个最容易出错的坑：加粗有两个来源。**

Word 里的加粗既可能来自手动按下的加粗快捷键（直接格式），也可能来自段落所用样式自带的效果，例如标题样式本身通常就是加粗的。

如果两种来源都输出加粗标记，结果会变成标题加粗的重复强调，既难读又冗余。正确做法是**先合并样式与直接格式，算出段落最终的有效格式，再判断这个格式是否需要在 Markdown 里显式表达**：样式带来的加粗不输出，只有直接格式带来的加粗才输出。Word 里还存在显式取消加粗的写法（加粗属性设为关闭），同样按最终有效值判断。

## 5. 总体架构

### 5.1 核心设计思想：分层加中间表示

架构上最重要的一个决策是：在读取 Word 和输出 Markdown 之间，插入一层与两者都无关的中间表示（IR，Intermediate Representation）。

为什么值得多这一层？如果把解析和渲染写成一条流水线里的耦合代码，那么表格转 HTML 还是 GFM、图片放目录还是内嵌 base64 这类需求，会直接撕开解析逻辑；而引入 IR 之后：

- 解析器只关心 Word 里有什么，渲染器只关心怎么写 Markdown，两边可以独立修改和测试
- 同一份 IR 可以对接多个渲染器（Markdown、HTML、未来的回写 Word）
- 可以写一个 IR 断言器直接对结构做自动化测试，不需要人工比对文本
- 将来要支持 .doc 或 .rtf，只需新增一个前端解析器，后半段完全复用

### 5.2 分层架构

```
┌─────────────────────────────────────────────────────────┐
│  输入层  Input                                          │
│  .docx 文件 / 文件夹批量 / 网页上传                     │
└────────────────────────┬────────────────────────────────┘
                         ▼
┌─────────────────────────────────────────────────────────┐
│  容器层  OPC Package                                    │
│  解压 docx（本质是 ZIP），解析关系表与各部分            │
│  document.xml / styles.xml / numbering.xml / media/ ... │
└────────────────────────┬────────────────────────────────┘
                         ▼
┌─────────────────────────────────────────────────────────┐
│  解析层  Parser            Word XML  ──►  IR            │
│  样式解析 / 列表编号还原 / 表格合并 / 图片 / 公式 / 修订 │
└────────────────────────┬────────────────────────────────┘
                         ▼
┌─────────────────────────────────────────────────────────┐
│  中间表示  IR（独立于 Word，也独立于 Markdown）         │
│  Document { meta, blocks[] }                            │
└────────────────────────┬────────────────────────────────┘
                         ▼
┌─────────────────────────────────────────────────────────┐
│  渲染层  Renderer          IR  ──►  Markdown 文本       │
│  表格策略选择 / 转义 / 空行归一 / HTML 降级             │
└────────────────────────┬────────────────────────────────┘
                         ▼
┌─────────────────────────────────────────────────────────┐
│  后处理与输出  Output                                   │
│  图片落盘 / 元信息头 / 目录 / 转换报告 / 写文件         │
└─────────────────────────────────────────────────────────┘
```

旁边还挂着两个横切模块，被所有层共用：

- **转换报告模块**：各层遇到降级、跳过、异常时统一往报告里写条目，记录位置、原因、处理方式
- **配置模块**：全局默认加单次调用覆盖，控制表格策略、图片策略、修订处理等所有开关

### 5.3 数据流（单篇转换）

```
1. 用户选择 PRD.docx
2. 解压为 OPC 包，读取关系表，定位各个部分
3. 解析 styles.xml    得到样式 ID 到语义角色的映射表
4. 解析 numbering.xml 得到列表编号定义表
5. 按文档顺序遍历正文的段落与表格
     段落  → 判定角色（标题 / 正文 / 列表 / 引用）→ 解析行内元素
     表格  → 解析行列、合并信息、单元格内容
     图片  → 登记到资源清单（此时不落盘）
6. 产出 IR 文档对象
7. IR 转 Markdown 文本（按配置选择表格策略、执行转义与归一化）
8. 提取图片写入资源目录，校正正文中的相对路径
9. 生成转换报告（统计信息加警告清单）
10. 输出 PRD.md、资源目录、转换报告.json
```

## 6. 中间表示（IR）设计

IR 是整个架构的枢纽，节点分两类：块级和行内。

### 6.1 块级节点

| 节点 | 关键字段 | 说明 |
| --- | --- | --- |
| `Heading` | level, inlines, source_style | 级别为 1 至 6，超出 6 级的降为加粗段落 |
| `Paragraph` | inlines, alignment | 普通正文 |
| `List` | ordered, items, start | items 内含子 List 以表达嵌套 |
| `Table` | rows, header_rows, merge_map | merge_map 记录每个格子的跨度与合并状态 |
| `Image` | path, alt, width | 图片引用 |
| `Quote` | blocks | 引用块 |
| `CodeBlock` | language, text | Word 里等宽样式的段落 |
| `ThematicBreak` | 无 | 对应分页符或分隔线 |
| `RawHtml` | html | 复杂表格等降级内容 |

### 6.2 行内节点

`Text`、`Bold`、`Italic`、`Strike`、`InlineCode`、`Link`（含地址与文字）、`FootnoteRef`、`LineBreak`（硬换行）、`Math`（存 LaTeX）。

### 6.3 为什么这样设计

行内样式支持任意嵌套（加粗里套斜体、链接里套加粗），所以用树形结构而非带标记的字符串。这样渲染时递归下降即可，转义逻辑集中在渲染层一处，不会散落到各处。

## 8. 技术选型

### 8.1 选型结论

| 层面 | 选择 | 理由 |
| --- | --- | --- |
| 语言 | Python 3.11 及以上 | OOXML 生态最成熟；XML 处理与文本处理表达力强 |
| XML 解析 | `lxml` | 比标准库快，且能完整保留命名空间信息 |
| 容器读取 | 标准库 `zipfile` | docx 本质就是 ZIP，不需要额外依赖 |
| 打包分发 | 打包为单文件可执行程序 | 目标机器无需安装 Python |
| 网页界面 | 内置轻量 HTTP 服务加单页 HTML | 不引入前端构建链，保持零依赖 |

### 8.2 同类工具调研

市面上确实已有不少成熟工具，值得逐一说明，因为这决定了本项目该做什么、不该重做哪一部分。

| 类型 | 代表工具 | 优势 | 短板 |
| --- | --- | --- | --- |
| 通用文档转换器 | Pandoc | docx 解析质量高，表格、脚注、图片均支持，命令行与批处理能力强 | 需额外安装程序；合并单元格的降级方式不可控；无结构化转换报告；样式映射不可配置 |
| 编程库 | Mammoth | 主张语义化转换，专为 docx 设计，输出 HTML 的质量好 | 主要面向 HTML；对合并单元格、列表编号还原的控制力更弱 |
| 官方开源方案 | MarkItDown（微软开源） | 一个入口支持 docx、pdf、pptx、xlsx 等多种格式并输出 Markdown，面向大模型场景设计 | 定位是给大模型读取的粗粒度文本，不以保真为目标，表格细节会丢失 |
| 在线转换网站 | 各类 docx 转 md 站点 | 免安装，打开网页点一下就能用 | 文档必须上传到第三方服务器，客户名、价格等信息会离开本机；不支持批量与报告 |

另有商业文档处理库（如 Aspose.Words 一类），能力完整、对合并表格的模型支持度高，但需付费授权，个人自用不划算。

**调研结论**：这些工具都值得用，但没有一个能同时满足本项目的核心诉求——中文 Word 模板的样式识别、合并单元格的可控降级、以及明确告诉你哪里转坏了的报告机制。因此本项目的定位不是重新发明转换器，而是在成熟内核能力之上，做贴合实际工作流的增强层。

**一个更省事的前置建议**：先花十分钟用 Pandoc 试转几份真实文档。如果它转出来的结果已经够用，这个项目可以先不做，或者只做包一层界面加出报告的部分；如果它的表格确实崩了，那就拿到了一批真实的失败样本，正好当作基准集的第一批素材。两种结果都不亏。

**说明**：以上对比基于对这几个工具的既有了解，本次编写文档时环境无法联网核实具体版本的细节。正式动手前建议用你的真实文档各试一遍，以实测结果为准。

### 8.3 为什么不把现成工具当内核

8.2 的表格已经列出各工具的差异，这里只讨论一个更实际的问题：能不能拿现成工具当解析内核，我们只在外面做策略层和报告层？

这条折中路线的吸引力很明显——开发量最小，解析质量直接继承成熟工具。但要接受两点代价：

- **能力上限被内核锁死**：本项目最需要控制的两件事，恰好都发生在解析阶段。合并单元格的信息如果在内核解析时就被压平丢失，外层的策略层再怎么设计也无从补救；样式到语义的映射同理，内核不给这个能力，外面就只能猜。
- **外部依赖与免安装目标冲突**：依赖一个需要单独安装的转换程序，会让打包分发变复杂，也难以保证在不同机器上行为一致。

**结论**：解析内核自研，因为它决定了后续所有能力的天花板。但这不等于要先写完内核再验证效果——先用 8.2 节的方法确认现成方案到底差在哪里，再决定投入多少。成熟工具也不浪费：用 Pandoc 的输出作为对照基线，放在测试环节（见 8.4）。

### 8.4 更好的用法：让 Pandoc 当对照基线

这是本项目一个额外的质量保障手段：在测试环境用 Pandoc 转同一份文档，把它的输出和我们自己的输出做结构对比。

如果 Pandoc 识别出了一个标题或一张表格而我们的工具漏了，那大概率是我们的解析有遗漏，相当于免费获得了一批别人已经踩过的坑。注意它只用于测试阶段的交叉验证，不进入产品运行时。

### 8.5 需要正面处理的现实问题

当前这台机器上**没有安装任何运行时**（Python、Node、.NET、Git 都没有）。这不是可以绕过的细节，它对交付方式有直接影响：

- 开发阶段需要先装 Python，或改选其他已有运行时的技术栈
- 交付阶段必须打包成免安装的可执行文件，否则用户拿到手跑不起来
- 如果坚持要双击就能用，打包是必选项，不能留到后期再补

### 8.6 Python 作为技术栈的评估

结论先说：Python 就是这个场景的最优解，而不是凑合能用。

| 层面 | 选型 | 理由 |
| --- | --- | --- |
| 核心解析 | `lxml` 直接操作 OOXML | 需要读取 `python-docx` 未完整暴露的信息 |
| 辅助库 | `python-docx` | 用于简单的段落与文本读取，不作为主力 |
| 容器读取 | 标准库 `zipfile` | docx 本质是 ZIP，无需额外依赖 |
| 打包分发 | PyInstaller 或 Nuitka | 产出免安装可执行文件 |

**需要特别注意的一点**：`python-docx` 很好用，但它有意简化了文档模型，列表编号的细节与合并单元格的完整信息都没有完整暴露出来，而这两块恰好是本项目最难、最需要精确处理的部分。所以关键部分必须用 `lxml` 直接读原始 XML，`python-docx` 只作辅助。这一点若没有提前意识到，很容易做到一半才发现走不通。

Python 的短板，如实说明：

- 打包成可执行文件后体积偏大（通常几十 MB），启动比原生程序慢一到两秒。对本场景完全可以接受。
- 需要先安装 Python 才能开发，而当前机器上什么都没有，这是第一步要解决的事。

备选方案（仅当 Python 遇到硬伤时才考虑）：

| 方案 | 优势 | 代价 |
| --- | --- | --- |
| .NET 加 OpenXML SDK | Windows 原生、打包体积小、启动快、OOXML 模型最完整 | 开发效率低一些，且该 SDK 偏文档操作而非文本抽取，代码量更大 |
| Node 加 mammoth.js | 可做纯前端、零安装的版本 | 控制力弱，表格处理上限低 |
| 纯浏览器方案 | 零安装，文档不出本机 | 能力天花板最低，合并单元格基本无解 |

### 8.7 交付形态：个人使用，建议本地网页版

前提是个人使用。这个前提本身砍掉了大量复杂度：不需要账号体系、不需要权限管理、不需要多用户隔离、不需要数据库、不需要部署方案。这一条能省下相当可观的工作量。

在此前提下，建议做成本地网页版：打包成一个可执行文件，双击后在浏览器中打开界面。

| 考量 | 本地网页版 | 桌面窗口版 |
| --- | --- | --- |
| Markdown 预览 | 浏览器自带渲染能力，可直接对照原文与结果 | 需自行引入渲染组件 |
| 拖拽、多文件、复制 | 浏览器原生支持最好，转完可直接全选复制 | 需要自己实现 |
| 迭代速度 | 改界面成本低 | 需学习桌面 UI 框架 |
| 批量处理 | 在同一个界面里顺手完成 | 需要额外开发 |
| 启动体验 | 需起本地服务，但可自动打开浏览器抹平 | 双击即用，无服务与端口 |
| 打包体积 | 与窗口版相当 | 与网页版相当 |

**决定性因素是预览**：转换完成后你的第一件事一定是确认转对没有，而浏览器免费提供了最好的 Markdown 渲染器。桌面窗口版在这方面要自己造轮子。

窗口版的优势是双击即用、没有服务进程和端口占用，这个优势可以抹平：打包后的可执行文件双击后自动启动本地服务并自动打开浏览器，使用体验与窗口应用基本一致，只是任务栏多一个图标。

命令行不作为主要交互方式，但会作为内部能力保留，用于批处理和自动化调试。日常使用走网页界面。

### 9.3 输出物约定

单篇转换产出三样东西：

```
输出目录/
├─ PRD.md                转换结果
├─ PRD.assets/           图片资源
│  ├─ PRD-img-001.png
│  └─ PRD-img-002.png
└─ PRD.report.json       转换报告
```

报告结构：

```json
{
  "source": "PRD.docx",
  "status": "ok",
  "stats": { "headings": 18, "tables": 6, "images": 4, "lists": 12, "words": 5321 },
  "warnings": [
    {
      "level": "warn",
      "kind": "table_merge",
      "where": "表格 3（第 42 段）",
      "detail": "检测到 2 级纵向合并，已按 GFM 模式用上一行值填充"

}
```

`status` 取值：`ok` 表示无警告；`warn` 表示有降级但有内容产出；`error` 表示转换失败。

## 10. 质量保障

### 10.1 核心难题：没有标准答案

Word 转 Markdown 不存在唯一正确输出。同一个表格，用 GFM 还是 HTML 都算对。这意味着不能靠输出与预期完全一致来做测试，否则测试会非常脆弱，稍微调整一下空行就全线飘红。

### 10.2 三层验证

**第一层：结构断言（自动化，覆盖最广）**

不比对全文，只断言关键结构：标题层级序列、表格行列数、图片数量、列表项与嵌套深度、警告条目。这层能捕获绝大多数真实缺陷，且不会因为空行调整而误报。

**第二层：基准集对比（回归防护）**

维护一组 `fixtures/*.docx` 和对应的人工确认过的 `.expected.md`。修改代码后跑全量对比，任何差异都要人工判断是改进还是回归；确认是改进就更新基准文件。

**第三层：往返校验（抽查）**

把转出的 Markdown 重新渲染为 HTML，与原文档在浏览器里的呈现做视觉对比。适用于复杂表格这类容易出错的场景。

### 10.3 基准文档集设计

这批样本的质量决定了整个工具的质量，建议优先准备。

| 样本 | 覆盖的结构 |
| --- | --- |
| 典型 PRD | 多级标题、段落、加粗斜体、超链接 |
| 字段清单 | 大表格、单元格内多段落、含竖线字符 |
| 权限矩阵 | 横向加纵向合并单元格 |
| 状态机说明 | 多级嵌套列表、图片、题注 |
| 含公式文档 | OMML 公式、行内与独立公式 |
| 带修订文档 | 插入、删除、批注 |
| 手打标题文档 | 完全不用样式、靠字号区分层级 |
| 杂乱文档 | 文本框、混合样式、异常结构（验证不崩溃） |

**建议**：直接从你历史积累的真实文档里挑 15 到 20 篇作为基准集，比人工构造样本有意义得多，因为真实文档里的意外才是真正的挑战。

## 11. 风险与对策

| 风险 | 影响 | 对策 |
| --- | --- | --- |
| 表格合并无法忠实还原 | 高 | 三种策略可选加报告明示；接受不可能 100% 保真是 Markdown 的固有局限 |
| 样式识别在中文模板下失效 | 高 | 三级判定策略；用真实文档集验证并持续补规则 |
| 目标机器无运行时，交付复杂 | 中 | 打包为免安装单文件程序，在开发早期就验证打包流程 |
| 保真度验证成本高 | 中 | 结构断言为主、人工确认为辅，只对基准集做人工确认 |
| 需求范围膨胀（什么都想转） | 中 | 严格守住分层边界；每一项降级都必须能写进报告 |

## 附录 A：Word 内容与 Markdown 的表达能力对照

| Word 能力 | Markdown | 处理方式 |
| --- | --- | --- |
| 多级标题 | `#` 至 `######` | 直接映射，超 6 级降为加粗段落 |
| 加粗 / 斜体 / 删除线 | `**` `*` `~~` | 直接映射 |
| 字体 / 字号 / 颜色 / 底纹 | 无 | 丢弃 |
| 下划线 | 无 | 默认丢弃，可用 HTML 标签保留 |
| 文字高亮 | 非标准语法 | 默认丢弃，可配置为 HTML 高亮标签 |
| 上标 / 下标 | 无原生语法 | 用 HTML 的上标下标标签 |
| 有序 / 无序列表 | `1.` `-` | 状态机还原实际编号 |
| 嵌套列表 | 缩进 | 每层 4 空格 |
| 表格（无合并） | GFM 表格 | 直接映射 |
| 表格（有合并） | 不支持 | 三种降级策略 |
| 图片（行内） | 图片语法 | 提取到资源目录 |
| 图片（浮动） | 无 | 降级为行内并记入报告 |
| 超链接 | 链接语法 | 直接映射 |
| 脚注 / 尾注 | 部分支持 | 转为 Markdown 脚注语法 |
| 题注 | 无 | 转为加粗段落 |
| 公式 | 部分支持 | 转 LaTeX，转不了的降级为图片 |
| 批注 | 无 | 可配置提取为清单 |
| 修订痕迹 | 无 | 按配置接受或标记 |
| 页眉页脚 / 水印 / 页码 | 无 | 丢弃 |
| 文本框 / 艺术字 | 无 | 抽取文本并记入报告 |

## 附录 B：决策结论

以下决策均已确认，作为开发前提：

| 编号 | 决策点 | 结论 |
| --- | --- | --- |
| D1 | 交付形态 | 本地网页版，打包为免安装可执行文件；命令行作为内部能力保留 |
| D2 | 使用范围 | 仅个人使用，因此不做账号、权限、多用户、数据库与部署方案 |
| D3 | 图片处理 | 默认自动提取到独立资源目录；占位符模式作为可选配置 |
| D4 | 是否需要反向转换 | 本期不做 |
| D5 | 下游平台 | 通用 Markdown，各平台语法差异后期按需适配 |
| D6 | 是否接入 AI 处理 | 不接入。工具做到产出干净 Markdown 为止，AI 处理放在下游 |
| D7 | 是否联网 | 不联网，不调用任何外部 API，完全本地运行 |

**动手前仍建议先做的两件事**：

1. 用 Pandoc 试转几份真实文档，确认它是否已经够用（见 8.2 节的前置建议）。
2. 挑 15 到 20 篇真实文档作为基准集，其中必须包含合并单元格密集的权限矩阵类文档。
